# AppBridge 拡張計画

## 1. 目的と基本方針

現在の `office-com-bridge` を発展させ、AI エージェントが複数の文書やアプリケーションを横断して操作できる、Windows デスクトップ向けのブリッジ基盤 **AppBridge** に育てる。

ただし、拡張は一度に行わない。次の **2段階を明確に分離**し、Phase 1 が安定してから Phase 2 に進む。

1. **Phase 1：Office 内で複数ドキュメントを扱えるようにする**
   - 対象アプリは Word / Excel / PowerPoint のまま。
   - 複数の文書・ブック・プレゼンテーションを登録し、明示的に選んで操作できるようにする。
2. **Phase 2：Office 以外のアプリケーションにも対応する**
   - Phase 1 の複数対象管理と実行基盤を土台に、アプリケーションごとのアダプターを追加する。
   - ブラウザーや Windows デスクトップアプリなどを対象候補とする。

**Phase 1 の完了条件に、Office 以外のアプリ対応を含めない。** また、Phase 2 のための抽象化は必要最小限に留め、Phase 1 の実装を過度に複雑化させない。

## 2. 現状

現行実装は、起動済みの Word / Excel / PowerPoint を対象にする Windows 専用のブリッジである。

- `Ctrl+Alt+O` で前景の Office ウィンドウを捕捉する。
- `127.0.0.1:8733` の HTTP/JSON API と `office` CLI を提供する。
- COM 操作を STA ワーカースレッドに集約する。
- よく使う読み書き操作に加え、汎用 COM 操作を提供する。
- OpenCode Skill とランチャーから利用できる。
- 書き込み確認、対象文書名の照合、読み取り上限、ログなどを備える。

現状の中心概念は「現在の対象」であり、複数の対象を安定した ID で保持して明示的に切り替える仕組みは未実装である。

## 3. 全体ロードマップ

| 段階 | 範囲 | 目的 | 完了後の状態 |
|---|---|---|---|
| **Phase 1** | Word / Excel / PowerPoint のみ | 複数文書の登録・識別・操作 | Office 文書を複数保持し、文書間の作業をエージェントが組み立てられる |
| **Phase 2** | Office + 他アプリ | アダプター方式で対応アプリを拡張 | 共通の実行基盤から、異なるアプリ固有の操作を呼び出せる |

# Phase 1：Office の複数ドキュメント対応

## 4. 目標

複数の Office 文書を同時に登録し、操作のたびに対象を明示できるようにする。

想定ユースケース：

- 2つの Word 文書を読み込み、内容を比較する。
- Excel の表を読み取り、そのデータを使って PowerPoint のスライドを作成・更新する。
- 複数の Excel ブックから情報を集め、別の Word 文書に反映する。
- 複数の文書を参照しながら、一つの文書を編集する。

これらの**業務ワークフロー自体は、まず Skill / エージェント側で組み立てる**。ブリッジに「Word 比較機能」や「Excel から PowerPoint を作る機能」を直接実装することは、初期スコープに含めない。

## 5. 設計方針

### 5.1 「現在の対象」から「対象レジストリ」へ

捕捉した文書を、プロセス内の対象レジストリに登録する。各対象には、ファイル名やウィンドウハンドルとは別に、ブリッジが発行する安定した `target_id` を付与する。

対象情報の例：

- `target_id`
- アプリ種別（`word` / `excel` / `powerpoint`）
- 文書名
- パス（取得できる場合）
- ウィンドウ情報
- 対象の状態（有効 / 消失 / 無効）
- 登録時刻などの診断情報

COM オブジェクト参照そのものと、利用者に返す対象メタデータは分離する。文書が閉じられたり参照が無効になったりした場合は、その対象を無効として扱い、別の文書へ黙って切り替えない。

### 5.2 対象を明示して操作する

すべての読み書き API と CLI に、対象を指定する仕組みを設ける。対象指定がない場合の扱いは明確にし、誤操作を避けるため、書き込み操作では暗黙の「現在の対象」に依存しない設計を優先する。

CLI のイメージ（コマンド名や構文は設計時に確定する）：

```text
office target capture
office target list
office target info <target-id>
office --target <target-id> word document read
office --target <target-id> excel range read A1:D20
```

既存 CLI との互換性を考慮し、移行期間は従来の「現在の対象」をデフォルトとして残すことも可能。ただし、複数文書を使う Skill では明示的な `target_id` 指定を必須にする。

### 5.3 COM の実行モデル

- COM 操作は既存の STA ワーカースレッドに集約する。
- 複数対象の保持は、複数スレッドから同時に COM を操作することを意味しない。
- 初期段階では要求を直列に処理し、正確性と対象の取り違え防止を優先する。
- COM 参照の寿命、ウィンドウと文書の対応、対象が閉じられた場合の失効処理を重点的にテストする。

### 5.4 読み取りと書き込みの安全性

- 読み取り結果には、対象 ID と文書識別情報を含める。
- 書き込み時には対象 ID と対象文書の整合性を再確認する。
- 対象が消失・失効している場合はエラーにし、別対象に自動フォールバックしない。
- 書き込み前の確認、`dry-run`、読み取りサイズ制限、構造化ログを維持する。
- 汎用 COM 呼び出しは副作用の大きい操作を間接的に実行できる可能性があるため、単純なメソッド名のブロックリストだけに依存しない。許可操作の範囲や権限レベルを見直す。

### 5.5 Skill 側で複数文書の仕事を組み立てる

最初に追加する Skill の例：

1. 比較する 2 つの Word 文書を、それぞれ別の `target_id` で読み取る。
2. エージェントが内容を比較し、差分や要約を作る。
3. 必要に応じて結果を指定した Word 文書へ書き込む。
4. 書き込み先と変更内容を明示し、実行前に確認する。

続いて、Excel の範囲を読み、PowerPoint の対象プレゼンテーションに反映するワークフローを作る。

ブリッジはアプリケーションの低レベル操作と安全な対象ルーティングに集中し、文書の意味解釈やワークフローの判断はエージェント側に置く。

## 6. Phase 1 の実装順序

### 1. 対象レジストリ

- `target capture`
- `target list`
- `target info`
- 必要に応じて `target remove`
- 無効参照・閉じられた文書の検出

### 2. API / CLI の対象指定

- 読み取り API に `target_id` を追加する。
- 書き込み API では対象を明示させ、対象の再検証を行う。
- エラー応答に対象 ID と失敗理由を含める。

### 3. 既存 Office 操作の移行

- Excel、Word、PowerPoint の既存操作を対象 ID 経由で実行できるようにする。
- 既存の「現在の対象」方式との互換性と移行方針を決める。
- STA ワーカーで複数対象を順番に扱うテストを追加する。

### 4. 複数文書用 Skill

- 2つの Word 文書を比較するワークフローを実装する。
- 次に Excel のデータを PowerPoint に反映するワークフローを実装する。
- 各操作で参照元・書き込み先の対象を取り違えないことを検証する。

### 5. 安全性と統合テスト

- 文書を閉じた後の操作
- 対象 ID の誤指定
- 同名ファイルや複数ウィンドウ
- 書き込み確認・`dry-run`
- 長い読み取り結果とタイムアウト
- COM エラー発生後のワーカー継続性

## 7. Phase 1 の完了条件

- [ ] 複数の Word / Excel / PowerPoint 文書を同時に登録できる。
- [ ] 各対象に一意な `target_id` があり、一覧・詳細を取得できる。
- [ ] すべての操作で対象を明示できる。
- [ ] 対象が閉じられた場合、無効対象への操作が安全に失敗する。
- [ ] 参照元と書き込み先を分けたワークフローが動作する。
- [ ] 2つの Word 文書の比較を Skill で実行できる。
- [ ] Excel のデータを PowerPoint に反映する Skill を実行できる。
- [ ] 既存の読み書き機能、確認手順、テストが維持される。

**Phase 1 完了までは、ブラウザーや Office 以外のアプリ対応を実装しない。**

# Phase 2：他アプリケーションへの対応

## 8. 目標

Phase 1 で確立した対象管理・操作実行・ログ・確認の仕組みを再利用し、Office 以外のアプリケーションを追加できる構造にする。

ここで初めて、プロジェクトを Office 専用ツールから、アプリケーション横断型の **AppBridge** として発展させる。

## 9. アーキテクチャ方針

アプリごとの操作モデルを無理に一つに統一せず、共通部分と固有部分を分ける。

```text
AI Agent / Skill
       │
       ▼
AppBridge CLI / HTTP JSON API
       │
       ▼
共通ランタイム
  ├─ 対象レジストリ
  ├─ 対象ルーティング
  ├─ Capability の公開
  ├─ 入力検証・確認
  ├─ エラー形式・ログ
  └─ 実行タイムアウト
       │
       ▼
アプリケーション別 Adapter
  ├─ Office Adapter（COM / STA）
  ├─ Browser Adapter（CDP / Playwright 等）
  └─ Windows UI Adapter（UI Automation 等）
```

### 9.1 共通化するもの

- 対象の識別・登録・状態管理
- 対象を指定した操作ルーティング
- アプリケーション種別と対象情報の公開
- 操作可能な機能（capabilities）の列挙
- リクエスト・レスポンス・エラーの基本形式
- 書き込み前の確認、監査ログ、タイムアウト
- CLI / HTTP API の共通的な利用方法

### 9.2 アダプターごとに残すもの

- 実際の接続方式
- アプリ固有のオブジェクトモデル
- 選択範囲、タブ、ページ、シートなどの固有概念
- 読み取り・書き込み操作の意味と制約
- スレッドモデルやセッション管理

Office の COM オブジェクトモデルを、ブラウザーや一般の Windows アプリに押し付けない。共通化するのは操作の外枠であり、すべてのアプリに同じ操作セットを要求しない。

## 10. 対応候補と順序

### 10.1 Browser Adapter

ブラウザーは、DOM を通じた構造的な読み書きが可能なため、次の候補とする。

想定機能：

- 既存ブラウザーのタブ／ページの列挙と識別
- ページタイトル、URL、DOM などの読み取り
- フォーム入力や明示的な要素操作
- タブやページの状態変化への対応

接続方式は CDP や Playwright などを検討する。既存のブラウザーセッションへの接続、対象タブの識別、ユーザーのログイン状態、許可する操作範囲は別途設計が必要である。

### 10.2 Windows UI Adapter

UI Automation などを利用し、ブラウザー DOM や Office COM で直接操作できないデスクトップアプリを対象にする。

想定機能：

- ウィンドウ・コントロールの列挙
- UI Automation ツリーを使った情報取得
- 対応するコントロールへの入力・操作
- UI 状態の変化や操作失敗の検出

UIA で扱えないアプリや独自描画 UI もあるため、万能な操作方式とは見なさない。必要な場合に限り、別方式を検討する。

### 10.3 追加アダプターの判断基準

アダプターを追加する前に、対象アプリで必要な読み取り・書き込みが構造的に実行可能か、対象を安定して識別できるか、失敗を検出できるかを検証する。

## 11. 名前とパッケージ構成

プロジェクト名として **AppBridge** を採用する。

移行は段階的に行い、名称変更と Phase 1 の複数対象対応を同時に進めて変更範囲を膨らませない。

構成案：

```text
appbridge/
  runtime/
    targets.py
    routing.py
    capabilities.py
    errors.py
    logging.py
  adapters/
    office/
      ...
    browser/
      ...
    windows/
      ...
  cli/
    ...
  skills/
    office/
      SKILL.md
    browser/
      SKILL.md
  tests/
```

- Phase 1 では既存実装を `Office Adapter` として整理しつつ、まず複数対象対応を完成させる。
- 共通ランタイムへの切り出しは、実際に複数アダプターが必要になる Phase 2 で本格化する。
- CLI 名、Python パッケージ名、リポジトリ名は一度に変更せず、互換性を確認しながら移行する。
- 公開・配布する前に、リポジトリ名、パッケージ名、コマンド名の利用可能性を確認する。

## 12. セキュリティと運用上の原則

AppBridge は、AI エージェントからユーザーの作業中のアプリを操作するため、対象の取り違えや意図しない副作用を避けることを優先する。

- ローカル利用を基本とし、API を不用意に外部公開しない。
- 書き込み対象を ID で明示する。
- 書き込み前に対象の有効性と文書識別情報を再検証する。
- 読み取り・書き込み・外部影響操作の権限を区別する。
- 汎用メソッド呼び出しの危険性を評価し、名前のブロックリストだけに依存しない。
- ログに対象、操作名、成否を記録する。機密文書の本文を無条件にログへ残さない。
- COM 操作などは一般にトランザクションとして扱えないため、失敗後の自動再試行が二重実行を起こさないようにする。
- 保存・クローズなど、ユーザーの明示操作に残す機能の範囲は、必要性と安全性を確認してから変更する。

## 13. 今回の決定事項

1. プロジェクト名は **AppBridge** とする。
2. 拡張は明確に **2段階**で行う。
3. **Phase 1 は Office の複数ドキュメント対応に限定**する。
4. Word 文書比較や Excel→PowerPoint のようなワークフローは、まず Skill / エージェント側で実現する。
5. **Phase 2 で初めて Office 以外のアプリケーションに対応**する。
6. Phase 2 ではアダプター方式を採用するが、Phase 1 の段階で過剰な汎用化はしない。
7. 正確な対象識別、明示的な対象指定、安全な失敗を機能拡張の前提とする。

## 14. 推奨する次の作業

直近では Phase 1 の設計・実装に集中する。

1. 対象レジストリと `target_id` の仕様を決める。
2. API / CLI の対象指定方式を決める。
3. COM 参照の寿命管理と対象失効時の挙動を実装する。
4. 既存 Office 操作を `target_id` 対応にする。
5. 複数 Word 文書の比較 Skill を作成する。
6. Excel→PowerPoint Skill を作成する。
7. Phase 1 の完了条件を満たした後に、Phase 2 のアダプター設計へ進む。

## 11. Phase 1 の対象選択 UX：実装方針

### 11.1 解決したい問題

複数文書を操作するには、エージェントが対象を識別できるだけでなく、利用者が意図した文書を AppBridge に登録できなければならない。一方、利用者に CLI コマンドや `target_id` を直接入力させることは避ける。

ここでは、次の3つを分けて考える。

1. **登録（capture / attach）**：操作可能な対象を AppBridge に認識させる。
2. **一覧・識別（list / info）**：登録済み対象を人とエージェントが確認できるようにする。
3. **操作先の指定（routing）**：個々の読み書き要求を、対象 ID で正しい文書へ送る。

これらは関連するが、同じ機能ではない。特に Phase 2 では、アプリごとに対象の登録方法が異なる可能性が高い。

### 11.2 Phase 1 の初期 UX：フォーカスしてホットキーを押す

**初期実装では、既存の `Ctrl+Alt+O` による捕捉操作を「現在の対象を置き換える」動作から「対象レジストリへ追加し、その対象を選択状態にする」動作へ拡張する。**

利用者の操作は次のとおり。

1. Word / Excel / PowerPoint で、登録したい文書を前面に出す。
2. `Ctrl+Alt+O` を押す。
3. AppBridge が文書を識別し、対象レジストリに追加する。
4. 別の文書も使う場合は、その文書を前面に出して同じ操作を行う。
5. OpenCode Skill が AppBridge API から対象一覧を取得し、各操作に適切な `target_id` を指定する。

利用者が `target_id` を覚えたり、CLI を直接操作したりする必要はない。ID はブリッジと Skill の内部的な識別子とする。

この方式を初期案とする理由：

- 既存のホットキーと捕捉処理を再利用でき、実装範囲が比較的小さい。
- Office の全プロセス・全文書を網羅的に列挙する仕組みを、最初から作らずに済む。
- 利用者自身が「この文書を今回の作業対象にする」と明示できる。
- 文書一覧 UI の実装を Phase 1 の必須条件にしなくてよい。

### 11.3 登録・一覧・失効の挙動

初期実装では、次の挙動を基準とする。

| 状況 | 期待する挙動 |
|---|---|
| 未登録の文書でホットキーを押す | 対象を登録し、新しい `target_id` を発行する |
| すでに登録済みの同じ文書でホットキーを押す | 重複登録せず、既存対象を再選択する |
| 別の文書でホットキーを押す | 既存対象を消さず、新しい対象を追加する |
| 登録済み文書が閉じられた | 対象を失効状態として扱い、操作をエラーにする |
| 登録対象が失効している | 別の対象へ自動的に切り替えない |
| 文書名が同じものが複数ある | 名前だけで区別せず、パス・ウィンドウ情報などを使って識別し、必要なら利用者に確認する |
| OpenCode が操作対象を選ぶ | 操作直前に対象一覧・状態を取得し、対象 ID を明示する |

「選択状態」は利便性のために保持してもよいが、複数文書を扱う Skill の読み書きは、その暗黙の選択状態に依存させない。とくに書き込み先は必ず明示する。

### 11.4 起動時一覧と最新一覧

AppBridge 起動時や OpenCode セッション開始時に対象一覧を提示することは補助的には有用だが、**その時点の一覧をセッション中ずっと正しいものとして扱ってはならない**。

文書はセッション中にも開閉・名前変更されるため、次の方針とする。

- 対象一覧 API はいつでも呼び出せるようにする。
- Skill はタスク開始時、および操作対象が重要になるタイミングで最新一覧を取得する。
- 書き込み直前には対象の有効性と識別情報を再検証する。
- 起動時に取得した一覧は、あくまで初期コンテキストとして扱う。

### 11.5 文書一覧ウィンドウは後続候補

現在開いている Office 文書を一覧表示し、チェックボックスや選択操作で登録できる小さな AppBridge ウィンドウは、将来の UX 改善候補とする。ただし、Phase 1 の最初の実装では必須にしない。

この UI を導入すると、Office の複数プロセスや複数文書の列挙、一覧と COM オブジェクトの対応付け、更新・閉じられた文書の検出、同名文書の区別などが必要になり、初期実装の複雑さが増す。ホットキー方式で対象管理の正しさを先に検証してから判断する。

ただし、ホットキー方式で実装する場合も、対象レジストリの内部設計を「ホットキーで登録されたものしか扱えない」構造に固定しない。

## 12. Phase 2 への影響と、Phase 1 で守るべき境界

対象選択の設計は Phase 2 に影響する。特に重要なのは、**「対象を登録する方法」と「登録済み対象を一覧・識別し、操作を振り分ける仕組み」を分離すること**である。

### 12.1 Phase 2 でも再利用する共通部分

Phase 1 では Office のみを扱うが、次の概念はアプリに依存しない形で設計する。

- `target_id` による対象の識別
- 対象の一覧・詳細取得
- 対象の状態（有効・失効・到達不能など）
- 操作要求に対象 ID を含めるルーティング
- 対象情報の共通フィールドと、アプリ固有メタデータの分離
- エラー形式、ログ、書き込み前の確認、タイムアウト
- 対象を取得・登録する手段を、共通の対象レジストリから切り離すこと

たとえば、共通の対象メタデータには `target_id`、`app_type`、`display_name`、`state` を持たせ、Office のファイルパスや COM 固有情報はアプリ固有のメタデータとして扱う。

### 12.2 アプリごとに異なってよい部分

対象の見つけ方・登録方法はアダプターごとに異なってよい。

- **Office**：前景ウィンドウをホットキーで捕捉する。将来は開いている文書の列挙 UI も検討する。
- **Browser**：ブラウザーへの接続後にタブ／ページを列挙し、選択・登録する方式が考えられる。
- **Windows UI**：前景ウィンドウを捕捉する方式、UI Automation で候補を列挙する方式などを検討する。

したがって、共通 API に Office 専用の `Ctrl+Alt+O` や COM オブジェクトの概念を埋め込まない。`capture` / `attach` / `discover` などの名前や責務は、実装時に意味を整理する。現時点では Office 向けコマンドとして実装し、将来の抽象化を先取りして複雑なプラグイン機構を作らない。

### 12.3 「対象レジストリ」と「現在の作業対象」

複数対象を保持するレジストリと、利用者が最後にホットキーで選択した対象は別の概念である。

- **対象レジストリ**：AppBridge が認識している対象の集合。
- **最後に選択した対象**：ホットキー操作などで最後に明示された対象。UI の表示や、単一対象向けの互換操作に利用できる。
- **要求ごとの対象**：個々の API / CLI 操作で明示する `target_id`。複数対象ワークフローではこれを正とする。

Phase 2 では、複数のブラウザータブや複数アプリのウィンドウが同時に対象になるため、この分離がさらに重要になる。最後に選択した対象を、すべての要求に暗黙適用する設計にはしない。

### 12.4 Phase 1 では避ける設計

- `target_id` をウィンドウハンドルやファイル名そのものにする。
- 文書名だけを対象の一意な識別子にする。
- ホットキーで最後に捕捉した対象を、すべての API が暗黙に使う。
- 対象が閉じられた際、似た名前の別文書へ自動的に切り替える。
- 共通対象モデルに COM オブジェクトや Office 固有の属性を必須として持たせる。
- Phase 2 を先取りして、初期段階から汎用プラグイン機構や複雑な UI を実装する。

### 12.5 この設計に基づく Phase 1 の追加タスク

- [ ] ホットキー捕捉を「置き換え」から「登録・再選択」に変更する。
- [ ] 同一文書の重複登録を防ぐ。
- [ ] 対象一覧 API を実装し、Skill から最新情報を取得できるようにする。
- [ ] 登録済み対象の状態と失効理由を一覧・詳細で確認できるようにする。
- [ ] 「最後に選択した対象」と、要求ごとの `target_id` を分離する。
- [ ] 同名文書・複数ウィンドウ・文書を閉じた後の参照をテストする。
- [ ] 対象メタデータの共通部分と Office 固有部分を分離する。
- [ ] 文書一覧 UI は必須スコープから外し、ホットキー方式の検証後に再評価する。

**設計上の結論：Phase 1 はホットキーで文書を明示的に登録する簡素な UX から始める。ただし、対象の登録方式は Office アダプター側の責務とし、対象 ID・一覧・状態管理・要求ごとのルーティングは将来の他アプリ対応でも再利用できる境界に置く。**
